# Escale 통합 설계

2026-11-13 소유자 최종 결정. 이전 기획과 충돌하면 이 문서를 우선한다. 구현 완료 기록은 `../구현_진행보고_escale.md`에서 별도로 관리한다.

## 1. Objective

혼자 여행하는 사람이 계획을 실행하고 돈을 관리한 뒤, 여행을 여권 스탬프로 남기는 하나의 앱이다. 다시 열 이유는 여행 전에는 준비, 여행 중에는 다음 행동과 남은 예산, 귀국 후에는 쌓이는 여행 성취다.

대상은 별도 계정 없이 직접 여행을 준비하는 개인이다. 핵심 불편은 흩어진 일정·예약, 이동 중 다음 행동 판단, 동행자와의 지출 정산이다. 가치 제안: **계획부터 귀국까지, 여행의 다음 행동을 한곳에서.**

## 2. Assumptions

- Expo·TypeScript·기존 로컬 저장 구조를 유지한다. 1단계는 로그인 없이 끝까지 작동해야 한다.
- TravPlan의 전체 정보 구조와 투래블의 계획 편의성을 통합하되 이름·로고·이미지·문구는 독자적으로 만든다.
- 기존 일기는 UI에서 제거한다. 기존 사용자 데이터·DB·마이그레이션은 보존한다.
- JEV는 기존 `api/recommend-places.ts`, `TravelPouch.tsx`, `pouchIntents` 등을 그대로 재사용한다. 별도 AI 인격이나 중복 추천 엔진을 만들지 않는다.
- 이 작업에서는 푸시·배포하지 않는다.

## 3. Recommended approach

기존 여행·돈·예약·검색 도메인을 재사용하고 화면 구성을 네 탭으로 정돈한다. 새 앱으로 재작성하는 것보다 데이터 보존과 솔로 운영이 쉽다. 일기 중심 UI를 유지하면 목적이 충돌하므로 일기 진입점은 제거한다.

흰색·옅은 회색 바탕, 선택·주요 버튼은 딥 틸, 코랄은 작은 강조에만 쓴다. 민트는 사용하지 않는다. 돛 로고를 재사용한다. 카드·버튼·타이포·간격은 기존 토큰과 공통 컴포넌트 한 체계로 통일한다. 장식보다 제목 → 핵심 정보 → 다음 행동 순서를 우선한다.

## 4. Scope (Must / Should / Could / Not now)

- **Must / 1단계:** 여행 생성 → 계획 → 오늘 → 돈(로컬 동행자 정산 포함) → 여권. 일기 UI 제거. 앱·공유 이름 Escale. 공통 UI 정돈.
- **Should / 1단계:** 계획의 시간표·캘린더·지도·예약이 같은 선택 날짜를 사용. loading·empty·error·validation·저장 실패 복구. 준비물·장소 검색·기존 사진 기능은 적합한 흐름에서 재사용.
- **Could / 후속:** 실제 생성한 국가별 스탬프 이미지 적용. 그전에는 직접 제작한 도형 placeholder를 명확히 사용.
- **Not now / 2단계:** 초대·역할·공동 편집·일정 댓글·공유 앨범. 1단계 전체 검증 전 착수하지 않는다.
- **Not now / 3단계:** JEV 초안 적용·되돌리기, 코스, 위치 공유, 멤버십.

## 5. User flow

여행 생성 → 계획(시간표 / 캘린더 / 지도 / 예약) → 오늘(다음 장소·이동·날씨·환율·지출) → 돈(예산·지출·영수증·동행자·정산) → 여행 성공 완료 → 귀국일에 여권 스탬프.

하단 탭은 **계획 / 오늘 / 돈 / 여권**이다. 추천·준비물·JEV는 관련 화면의 실제 동작하는 진입점으로 연결한다. 구현 전 버튼이나 가짜 날씨·환율·이동 정보는 노출하지 않는다. JEV는 “지금 출발해야 해요”, “오늘 예산 70% 썼어요”처럼 같은 목소리로 상태와 행동을 연결한다. 사실 근거가 없으면 단정하지 않는다.

## 6. Data / API design

- 일정은 기존 `PageEntry`, 여행은 `TripWorkspace`를 원본으로 삼는다. 일기 데이터의 존재와 화면 노출을 분리한다.
- 계획 화면의 선택 날짜는 공통 상위 상태 하나로 유지한다. 날짜·시간대 기준을 모든 보기에서 공유한다.
- 정산은 기존 돈 도메인 계산을 재사용한다. 로컬 동행자 ID는 향후 계정 ID와 분리한다. 금액 단위·환율·반올림 규칙을 유지한다.
- 여권 스탬프에는 여행 ID·국가 코드·국가명·도시·귀국 날짜·디자인 변형을 둔다. 성공 완료와 귀국일 도래를 모두 확인한다. 재실행·탭 전환·날짜 변경으로 중복 발급하지 않도록 여행과 국가 조합을 식별자로 삼는다. 같은 나라를 다시 방문한 다른 여행은 별도 스탬프다.
- 완료 여부를 단순 날짜 경과로 추정하지 않는다. 취소 여행을 성공으로 처리하지 않는다. 구체적인 완료 상태 저장 방식은 기존 모델 확인 후 결정하고 보고서에 기록한다.
- 스탬프 발급 상태는 일기와 분리한 로컬 저장으로 추가한다. 기존 데이터 삭제나 변환을 요구하지 않는다.
- 1단계를 위해 새 협업 서버를 만들지 않는다. 실시간 정보의 네트워크 실패는 화면에 설명하고 로컬 핵심 기능을 유지한다.

## 9. Risks

이전 iCloud 파일 접근 차단은 해소됐다. 병행 디자인 작업의 변경을 기능 변경과 섞지 않는다. 복사본으로 미확인 원본을 덮어쓰지 않는다. 일기 제거 중 백업·저장 호환 코드까지 삭제하지 않는다. 귀국일·시간대·중복 발급, 동행자 삭제 후 정산 보존, 외부 API 실패가 핵심 검증 대상이다.

### 구조

- **원본은 서버의 공유 여행, 기기에는 사본.** 소유자가 공유를 시작할 때 그 여행만 복사한다. 개인 전체 백업(`cloudSync`)과 섞지 않는다.
- **엔티티 단위 revision.** 공유 여행은 `settings`·`meta`(예산·일정 계획·경로)와 일정·준비물·지출·공금·송금·예약·댓글·사진을 각각 엔티티로 나눈다. 서버는 여행별 순번을 올리며 엔티티마다 마지막 revision을 둔다. 같은 엔티티의 `baseRevision`이 다르면 409로 거부한다. 문서의 여행 단위 revision보다 충돌이 적고, 조용한 덮어쓰기는 여전히 없다.
- **기기 쪽은 비교로 변경을 만든다.** 화면 저장 경로를 바꾸지 않고, 마지막으로 서버와 맞춘 기준 사본과 현재 기기 사본을 비교해 변경을 만든다. 엔티티마다 전송 중 작업은 하나다. 전송 전 작업을 기록해 앱이 꺼져도 같은 operationId로 다시 보낸다(서버는 operationId로 중복 적용을 막는다).
- **충돌은 사용자가 고른다.** 기기에 보내지 않은 변경이 있는 엔티티에 다른 사람의 변경이 오면 기기 내용을 유지하고 충돌로 표시한다. "내 것 보내기"(상대 revision 기준으로 다시 보냄) / "상대 것 받기" 중 고른다.
- **권한은 서버 규칙에서 강제.** owner=초대·역할·여행 설정, editor=일정·돈·준비물·예약·사진, viewer=조회·댓글. 댓글 수정은 작성자, 삭제는 작성자·owner. 사진 삭제는 올린 사람·owner. 화면에서는 같은 규칙으로 버튼을 숨기고, 서버가 거부하면 기준 사본으로 되돌리고 알린다.
- **멤버 = 돈 계산의 동행자.** `TripMember.memberId`는 기존 `Member.id`다. 참가자는 아직 연결되지 않은 동행자 중 본인을 고르거나 새 이름으로 참가한다. 탈퇴·내보내기 후에도 지출·정산의 동행자 기록은 지우지 않는다.
- **초대 토큰**은 32바이트 난수, 서버에는 SHA-256 해시만 보관한다. 기본 만료 7일, owner가 회수할 수 있다. 같은 사람이 다시 수락해도 멤버는 하나다.

### 어댑터

| 포트 | 구현 | 검증 |
|---|---|---|

출시 빌드는 `EXPO_PUBLIC_SHARED_TRIPS=1`과 로그인 세션이 있을 때만 공유 메뉴를 보인다. 서버가 없으면 공유 메뉴를 노출하지 않는다(가짜 버튼 금지). 개발 빌드는 기기 내 허브로 "다른 사람으로 참가"를 흉내 내 두 멤버 흐름을 한 기기에서 확인한다. 이 흉내 사본은 엔티티 ID에 접미사를 붙여 같은 수첩 안의 ID 충돌을 피한다.
